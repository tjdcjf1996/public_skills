# 실제 코드를 설명하고 서술하는 연습

운영 인계·완성 코드 이해에는 먼저 구조와 결정 근거를 설명한다. 서술 연습을 요청받으면 아래 질문 축에서 현재 이해에 필요한 것 하나를 골라 진행한다. 특정 시험의 예상 정답을 보장하는 용도가 아니다.

## 먼저 만들 설명 근거

현재 코드와 관련 대화·결정·테스트를 읽고, 기존 인계 문서에 주요 기능별로 다음 연결을 남긴다. 모든 구현 세부에 ID를 붙이거나 같은 내용을 여러 문서에 반복하지 않는다.

- **무엇을 요청했는가:** 실제 사용자 지시와 업무 제약. 과거 기록이 없으면 ‘당시 지시 확인 불가’로 쓴다.
- **무엇을 선택했는가:** 비교했던 방식, 누가 무엇을 선택했는지, 선택 당시 알려진 장단점. 나중에 찾은 개선점은 당시 판단과 분리한다.
- **어떻게 구성됐는가:** 주요 파일·함수의 책임과 호출 순서, 데이터·상태의 이동. 현재 파일에서 확인한 경로·심볼·줄 위치를 쓴다. 예정 구조를 구현된 것으로 쓰지 않는다.
- **왜 그런 결과가 나오는가:** 대표 정상·예외 입력이 어떤 분기를 통과해 어떤 결과를 만드는지 보여 준다. 중요한 실제 코드 발췌를 읽기 쉬운 길이로 제시한다.
- **어디까지 확인했는가:** 실행한 검사와 그 의미, 미실행·미검증·외부 환경의 한계. 테스트 존재와 실행 성공은 구별한다.
- **무엇을 바꿀 수 있는가:** 현재 방식의 대가, 대안이 유리해질 조건, 수정할 책임·계약·관련 테스트. 근거 없는 속도·안전성·확장성 우수 주장을 피한다.

대화에도 핵심 경로와 선택 이유를 직접 설명한다. 문서 링크만 전달하거나 함수 목록만 늘어놓지 않는다. 용어를 모르면 일상적인 표현과 작은 입력 예로 다시 설명한다.

## 한 문제씩 확인

1. 설명한 범위에서 질문 하나를 고른다. 예를 들어 “어떤 요구 때문에 이 구조를 선택했고, 다른 방식과 비교해 무엇을 얻고 포기했나요?” 또는 “이 입력은 어느 함수와 조건을 거쳐 이 결과가 되나요?”처럼 묻는다. 한 질문에 모든 축을 몰아넣지 않는다.
2. 사용자가 답할 때까지 기다린다. 모범답안·채점·다음 문제를 같은 메시지에 자동으로 내놓지 않는다. 힌트 요청에는 관련 파일·함수와 생각할 기준부터 제공한다.
3. 답변을 실제 코드와 대조해 **맞는 부분, 빠진 연결, 사실과 다른 설명**을 구별한다. 틀린 부분의 코드·입력 예를 짚고 필요한 개념만 재설명한다. 암기한 문장과 새로운 입력에 대한 이해를 혼동하지 않는다.
4. 피드백 뒤 사용자가 다시 답하거나 다음 질문을 선택할 수 있게 한다. 모범답안을 요청하면 보여 줄 수 있으나 읽었다는 사실을 이해 확인으로 기록하지 않는다. 사용자의 선택이나 수행 경험을 대신 지어낸 1인칭 답변을 만들지 않는다.
5. `STATUS.md` 또는 기존 학습 메모에 확인한 주제, 답변으로 확인된 범위, 보완할 개념, 코드 기준을 남긴다. 기술 완료 여부와 이해 상태는 독립적이다. “완벽히 이해함” 대신 “오류 처리 분기는 답변으로 확인, 저장 실패 처리는 미확인”처럼 범위를 적는다.

질문 축은 요구와 지시 / 대안과 선택 이유 / 알고리즘의 처리 순서·정확성 조건·시간과 공간 비용 / 코드 구성과 데이터 흐름 / 오류·권한 경계 / 검증 근거 / 한계와 개선이다. 설계의 의사코드와 현재 코드가 일치하는지도 설명하게 할 수 있다. 매번 전부 묻지 않는다. 사용자가 시간이 없어 건너뛰면 그 요청을 따르되 미확인 상태로 남긴다. 현재 코드로 확인할 수 없는 과거 의도나 외부 시스템의 동작은 정답으로 요구하지 않는다.
