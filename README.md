# Software Design & Development Skills

개인적으로 쓰는거 편하게 쓰려고 모아놓은 것이나 쓰셔도 됩니다.

요구사항 분석부터 설계, 구현, 테스트, 보안 검토와 인계까지 지원하는 Codex 스킬 모음입니다. 신규 서비스 개발, 기존 기능 개선, 내부 업무 도구 제작에 필요한 작업을 단계별로 수행합니다.

대화, 기획 문서, 이슈와 기존 코드를 근거로 결정을 내리고, 구현 결과를 검증 기록과 연결합니다. 개발자는 각 단계의 결과와 대안을 검토하며 다음 작업을 선택합니다.

## 스킬 구성

각 스킬은 독립적으로 호출할 수 있습니다. 프로젝트 전체에 적용하거나, 기존 코드의 설계 검토·테스트처럼 필요한 부분만 사용할 수 있습니다.

| 스킬                                                  | 역할                       | 주요 결과물                                 |
| ----------------------------------------------------- | -------------------------- | ------------------------------------------- |
| [problem-analysis](problem-analysis/SKILL.md)         | 문제와 현재 상황 분석      | 해결할 문제, 자료 분석, 확인할 질문         |
| [project-planning](project-planning/SKILL.md)         | 요구사항과 개발 범위 정리  | 확정 요구, 우선순위, 완료 기준              |
| [solution-design](solution-design/SKILL.md)           | 구조와 구현 계획 설계      | 데이터·인터페이스·파일 책임, 작업 분리 계획 |
| [feature-build](feature-build/SKILL.md)               | 기능 단위 구현             | 코드 변경, 관련 테스트, 실행 결과           |
| [test-run](test-run/SKILL.md)                         | 요구사항 기반 테스트       | 정상·예외·경계 사례, 실패 재현              |
| [security-review](security-review/SKILL.md)           | 보안 검토                  | 코드 근거가 있는 위험, 우선순위와 개선 방향 |
| [acceptance-review](acceptance-review/SKILL.md)       | 요구사항 충족 여부 검증    | 기능별 검증 결과, 누락과 미검증 범위        |
| [project-handoff](project-handoff/SKILL.md)           | 운영·유지보수를 위한 인계  | 실행 방법, 설계 결정, 확인된 한계           |
| [delivery-workflow](delivery-workflow/SKILL.md)       | 진행 상태와 다음 작업 안내 | 현재 단계, 다음 스킬과 작업 범위 추천       |
| [change-impact](change-impact/SKILL.md)               | 기존 기능 변경의 영향 조사 | 호출 경로, 호환성, 데이터 전환과 회귀 위험  |
| [root-cause-debugging](root-cause-debugging/SKILL.md) | 오류 재현과 원인 추적      | 재현 사례, 가설별 증거, 최소 수정 방향      |
| [code-review](code-review/SKILL.md)                   | 구현 변경분 리뷰           | 실제 결함, 회귀, 중요한 테스트 공백         |

## 사용 예시

다음 예시는 각각 별도의 요청입니다. 앞 단계 결과를 확인하고 필요한 시점에 호출합니다.

### 새 기능을 시작할 때

```text
$problem-analysis
고객 문의와 현재 주문 처리 코드를 읽고 해결할 문제를 정리해 줘.
추가로 확인할 업무 기준과 질문별 이유를 알려 줘.
```

```text
$project-planning
담당자 답변을 반영해서 주문 취소 기능의 요구사항을 정리해 줘.
확정된 정책, 미정 사항, 이번에 구현할 범위와 완료 기준을 구분해 줘.
```

```text
$solution-design
확정된 요구사항을 기존 구조에 맞춰 설계해 줘.
구현 파트와 파일 책임을 나누고 워크트리 분리가 유리한지도 설명해 줘.
```

### 구현과 검토를 반복할 때

```text
$feature-build
설계의 P1만 구현하고 관련 테스트를 실행해 줘.
변경 이유와 실제 동작을 설명한 뒤 멈춰.
```

```text
$test-run
P1의 완료 기준을 바탕으로 정상·예외·경계 사례를 검증해 줘.
실패가 있으면 재현 방법과 영향을 정리해 줘.
```

```text
$security-review
주문 취소 API의 권한 검사와 입력 검증을 검토해 줘.
실제 코드 근거와 최소 수정 방향을 보고해 줘.
```

### 기능을 마무리할 때

```text
$code-review
이번 변경과 관련 호출 경로를 검토해 줘.
사용자에게 영향을 주는 결함과 회귀를 근거와 함께 설명해 줘.
```

```text
$acceptance-review
확정 요구와 현재 구현을 대조해 누락과 회귀를 확인해 줘.
실제 검증한 항목과 미검증 항목을 구분해 줘.
```

```text
$project-handoff
검증 결과를 바탕으로 실행 방법, 주요 설계 결정과 남은 한계를 정리해 줘.
```

다음 작업을 판단하기 어려우면 `$delivery-workflow 현재 진행 상태를 확인하고 다음 작업을 추천해 줘.`라고 요청합니다. 이 스킬은 선택하지 않은 단계를 자동 실행하지 않습니다.

### 기존 기능을 바꾸거나 오류를 조사할 때

```text
$change-impact
주문 상태값 변경이 API 소비자와 기존 저장 데이터에 미칠 영향을 조사해 줘.
아직 코드는 수정하지 말고 필요한 전환과 회귀 검사를 정리해 줘.
```

```text
$root-cause-debugging
첨부한 실패 로그와 재현 입력으로 원인을 좁혀 줘.
관찰한 증거와 가설을 구분하고, 최소 수정 방향을 설명해 줘.
```

변경 영향 분석은 수정 전에, 디버깅은 실패 원인이 불명확할 때, 코드 리뷰는 변경분을 검토할 때 사용합니다. 세 스킬을 매번 추가로 실행할 필요는 없습니다.

## 작업 기록

프로젝트의 기존 문서 구조를 우선 사용합니다. 정해진 위치가 없으면 `docs/workflow/`에 단계별 기록과 `STATUS.md`를 남깁니다.

- **요구와 결정:** 입력 근거, 확정된 기준, 대안과 선택 이유
- **구현:** 변경 파일, 요구사항 연결, 파트별 진행 상태
- **검증:** 실행 명령, 입력과 기대 결과, 실제 결과, 실패·미실행
- **인계:** 실행 방법, 완료 범위, 운영·유지보수 시 고려할 한계

기존 문서와 원자료를 보존하며, 기록에는 실제 결정과 실행 결과만 반영합니다. 상세 근거는 문서에 남기고 대화에서는 검토에 필요한 핵심을 설명합니다.

## 설치와 조회

이 묶음에는 **독립된 스킬 12개**가 들어 있습니다. 전체를 사용하려면 각 스킬 폴더와 그 안의 참고 파일을 함께 설치해야 합니다. 한 번의 설치 요청으로 전체 폴더를 함께 설치할 수 있지만, `delivery-workflow` 하나만 설치하면 나머지가 자동 설치되지는 않습니다.

로컬 설치는 사용할 범위에 따라 다음 위치를 선택합니다.

| 범위                                 | 위치                         |
| ------------------------------------ | ---------------------------- |
| 특정 프로젝트에서 사용               | 프로젝트의 `.agents/skills/` |
| 사용자 계정의 여러 프로젝트에서 사용 | `~/.agents/skills/`          |

예를 들어 프로젝트에 설치한 폴더 구조는 다음과 같습니다.

```text
.agents/skills/
├── problem-analysis/SKILL.md
├── project-planning/
│   ├── SKILL.md
│   └── assets/
├── solution-design/SKILL.md
├── feature-build/SKILL.md
├── test-run/SKILL.md
├── security-review/SKILL.md
├── acceptance-review/SKILL.md
├── project-handoff/SKILL.md
├── change-impact/SKILL.md
├── root-cause-debugging/SKILL.md
├── code-review/SKILL.md
└── delivery-workflow/
    ├── SKILL.md
    └── references/
```

Codex CLI에서 `/skills` 또는 `$`로 발견된 스킬을 조회·선택합니다. 설치한 스킬이 보이지 않으면 경로와 비활성화 설정을 확인하고 Codex를 다시 시작합니다. 설치 경로와 조회 방법은 [공식 스킬 안내](https://learn.chatgpt.com/docs/build-skills)를 기준으로 합니다.

현재 원본 폴더를 보관하거나 README를 읽는 것만으로 설치되지는 않습니다. Git으로 소스를 가져온 뒤 각 스킬 폴더를 위 검색 경로에 배치하는 방식으로도 전체를 사용할 수 있습니다. 프로젝트의 기존 `.agents/skills/`나 동명 스킬을 덮어쓰지 않도록 먼저 확인합니다. 묶음 설치에 플러그인이 필수는 아니며, 플러그인으로 배포하려면 별도 패키징이 필요합니다.

Codex에 다음처럼 요청할 수 있습니다.

```text
https://github.com/tjdcjf1996/public_skills 의 스킬 12개를 모두 설치해 줘.
저장소 구조와 현재 환경의 스킬 검색 경로를 확인하고,
각 SKILL.md와 필요한 assets/references를 함께 설치해.
기존 동명 스킬은 덮어쓰지 말고 충돌을 알려 줘.
설치 후 발견되는 이름과 호출 방법만 보고하고 개발 작업은 시작하지 마.
```

직접 터미널에서 원본을 가져올 수도 있습니다.

```sh
git clone https://github.com/tjdcjf1996/public_skills.git
```

복제 후 저장소 루트의 스킬 폴더 12개를 원하는 `.agents/skills/` 위치에 참고 파일과 함께 배치합니다. 복제만으로 자동 등록되는 것은 아닙니다. README와 Git 메타데이터는 스킬 폴더 안으로 복사할 필요가 없습니다.

## 실행 환경과 외부 스킬

이 스킬들은 개발 절차를 안내하는 지침입니다. 실제 파일 수정, 서버 실행, 테스트와 서브에이전트 사용은 실행 중인 Codex 환경의 도구·권한에 따릅니다. 설치 자체가 개발 도구나 외부 서비스 연결을 준비해 주지는 않습니다.

필요한 작업에서는 설치된 공개 스킬의 원문을 확인해 활용할 수 있습니다. 외부 스킬과 실행 도구는 이 모음에 포함되지 않으며 별도로 확인합니다. 커밋·배포·외부 전송은 사용자가 요청한 범위에서 수행합니다.
