# Software Design & Development Skills

개인적으로 쓰는거 편하게 쓰려고 모아놓은 것이나 쓰셔도 됩니다.

요구사항 분석부터 설계, 구현, 테스트, 보안 검토와 인계까지 지원하는 Codex 스킬 모음입니다. 신규 서비스 개발, 기존 기능 개선, 내부 업무 도구 제작에 필요한 작업을 단계별로 수행합니다.

대화, 기획 문서, 이슈와 기존 코드를 근거로 처리 방식의 장단점을 비교합니다. 개발자가 방식을 선택하면 AI가 해당 범위를 작업하고, **내 지시와 선택이 어떤 코드·구조·결과로 이어졌는지** 설명합니다. 동작하는 결과물뿐 아니라 개발자가 그 구조와 한계를 자신의 말로 설명할 수 있는 것을 목표로 합니다.

## 내가 선택하고 이해하는 작업 흐름

**기획 전체 이해 → 구조·알고리즘 선택과 이해 확인 → 구현 요청 → 실행 능력 확인 → 병렬 또는 순차 구현 → 메인 통합·검수 → 실제 코드 설명**으로 진행합니다. 코딩 전에 이번 구현 범위 전체의 핵심 설계를 이해하고, 다음 단계나 구현 묶음은 직접 선택합니다.

설계에서는 핵심 알고리즘마다 목적과 입력·출력, 대안의 장단점, 의사코드, 예시 입력의 중간값과 결과, 정확성이 성립하는 조건, 시간·공간 비용과 한계를 설명합니다. 질문은 하나씩 받고 이해 상태는 알고리즘별로 남깁니다. 모든 코드 세부를 사전에 안다고 보장하는 대신, 중요한 미정 결정과 이해 공백을 코딩 전에 확인합니다. 구현 중 새로 드러난 결정은 다시 설명받고 선택합니다.

구현을 시작할 때 실제 서브에이전트 도구·권한과 파트 독립성을 확인합니다. 공통 계약과 파일 책임을 나눌 수 있으면 독립 파트를 병렬로 처리하고, 도구가 없거나 결합도가 높으면 같은 범위를 순차 처리합니다. 병렬 작업의 결과는 메인이 실제 코드를 읽고 통합 검사한 뒤 설명합니다. 에이전트별 완료 보고만으로 성공 처리하지 않으며, 병렬 작업이 항상 더 빠르다고 가정하지 않습니다.

기능을 만들어 달라는 요청만으로 저장 방식·책임 분리·핵심 계산·오류 정책까지 AI에게 맡긴 것으로 보지 않습니다. 아직 정하지 않은 중요한 결정은 추천안과 실질적인 대안을 비교하고 기다립니다. 추천안에도 단점과 포기하는 것을 표시합니다. 이미 선택한 방식은 다시 묻지 않으며, 변수명·서식 같은 사소한 선택에 매번 승인 절차를 만들지는 않습니다. 특정 판단을 맡기고 싶으면 그 범위를 명시하면 됩니다.

결과 설명에는 다음 내용이 연결됩니다.

- 실제 요청과 제약, AI의 제안, 내가 선택한 방식 또는 위임한 판단
- 선택 때문에 생긴 파일·함수의 책임, 데이터 흐름과 중요한 분기
- 대표 입력이 실제 코드의 어디를 거쳐 어떤 결과로 바뀌는지
- 검증한 효과와 미검증 범위, 장단점과 다른 방식이 유리해지는 조건
- 개선하려면 바꿀 코드·계약과 다시 확인할 테스트

핵심 설명은 대화에서도 보여 주고 상세 근거는 기존 단계 기록에 남깁니다. 과거 지시 기록이 없다면 현재 코드의 구조와 의도 추정을 구분합니다. 실제로 하지 않은 선택을 사용자의 판단으로 꾸미지 않습니다.

설명 후에는 자신의 말로 답할 질문 하나를 받습니다. 답변 전에 모범답안을 붙이지 않고, 답한 뒤 코드 근거로 맞는 부분·누락·오해를 피드백합니다. **테스트 통과, 진행 동의, 코드 이해는 별개**로 기록합니다. 이해 확인을 건너뛸 수 있지만 ‘다음으로’라고 했다는 이유로 이해 완료로 표시하지 않습니다. 한 질문에 답한 것만으로 전체 코드를 완전히 이해했다고 보장하지도 않습니다.

## 스킬 구성

각 스킬은 독립적으로 호출할 수 있습니다. 프로젝트 전체에 적용하거나, 기존 코드의 설계 검토·테스트처럼 필요한 부분만 사용할 수 있습니다.

| 스킬                                                  | 역할                       | 주요 결과물                                 |
| ----------------------------------------------------- | -------------------------- | ------------------------------------------- |
| [problem-analysis](problem-analysis/SKILL.md)         | 문제와 현재 상황 분석      | 해결할 문제, 자료 분석, 확인할 질문         |
| [project-planning](project-planning/SKILL.md)         | 요구사항과 개발 범위 정리  | 확정 요구, 우선순위, 완료 기준              |
| [solution-design](solution-design/SKILL.md)           | 구조와 구현 계획 설계      | 데이터·인터페이스·파일 책임, 작업 분리 계획 |
| [feature-build](feature-build/SKILL.md)               | 기능 단위 구현             | 코드 변경, 관련 테스트, 실행 결과           |
| [test-run](test-run/SKILL.md)                         | 요구사항 기반 테스트       | 정상·예외·경계 사례, 실패 재현              |
| [security-review](security-review/SKILL.md)           | 보안 검토                  | 코드 근거가 있는 위험, 우선순위와 개선 방향 |
| [acceptance-review](acceptance-review/SKILL.md)       | 요구사항 충족 여부 검증    | 기능별 검증 결과, 누락과 미검증 범위        |
| [project-handoff](project-handoff/SKILL.md)           | 코드 이해·서술 연습·인계   | 지시와 코드 연결, 실행법, 장단점, 이해 피드백 |
| [delivery-workflow](delivery-workflow/SKILL.md)       | 진행 상태와 다음 작업 안내 | 현재 단계, 다음 스킬과 작업 범위 추천       |
| [change-impact](change-impact/SKILL.md)               | 기존 기능 변경의 영향 조사 | 호출 경로, 호환성, 데이터 전환과 회귀 위험  |
| [root-cause-debugging](root-cause-debugging/SKILL.md) | 오류 재현과 원인 추적      | 재현 사례, 가설별 증거, 최소 수정 방향      |
| [code-review](code-review/SKILL.md)                   | 구현 변경분 리뷰           | 실제 결함, 회귀, 중요한 테스트 공백         |

## 사용 예시

다음 예시는 각각 별도의 요청입니다. 앞 단계 결과를 확인하고 필요한 시점에 호출합니다.

### 새 기능을 시작할 때

```text
$problem-analysis
고객 문의와 현재 주문 처리 코드를 읽고 해결할 문제를 정리해 줘.
실무자에게 바로 보낼 질문을 관련 기준끼리 묶어 한 문장으로 먼저 줘.
이유와 추가 확인 사항은 분석 기록에 남겨 줘.
```

```text
$project-planning
담당자 답변을 반영해서 주문 취소 기능의 요구사항을 정리해 줘.
확정된 정책, 미정 사항, 이번에 구현할 범위와 완료 기준을 구분해 줘.
```

```text
$solution-design
확정된 요구사항을 기존 구조에 맞춰 설계해 줘.
중요한 미정 결정부터 추천 방식과 대안의 장단점을 설명하고 내 선택을 기다려.
이번 범위 전체 구조와 핵심 알고리즘의 의사코드·처리 예·정확성 조건·시간과 공간 비용을 설명해 줘.
내 이해를 하나씩 확인하고 공통 계약과 독립 파트를 설계해 줘. 아직 코딩하지 마.
```

### 구현과 검토를 반복할 때

```text
$feature-build
이해하고 선택한 설계의 이번 구현 묶음을 시작해 줘.
실제 서브에이전트 지원과 작업 독립성을 먼저 확인해 가능하면 병렬로, 아니면 순차로 구현해 줘.
메인이 결과를 통합하고 전체 연결과 관련 테스트를 직접 검수해 줘.
새로운 중요한 결정이 있으면 먼저 비교하고 내 선택을 기다려.
구현 뒤 설계한 알고리즘과 실제 함수·분기·입력 흐름을 대조해서 설명해 줘.
내가 이해했는지 질문 하나로 확인한 뒤 다음 묶음은 기다려.
```

```text
$test-run
P1의 완료 기준을 바탕으로 정상·예외·경계 사례를 검증해 줘.
실패가 있으면 재현 방법과 영향을 정리해 줘.
```

```text
$security-review
주문 취소 API의 권한 검사와 입력 검증을 검토해 줘.
실제 코드 근거와 최소 수정 방향을 보고해 줘.
```

### 기능을 마무리할 때

```text
$code-review
이번 변경과 관련 호출 경로를 검토해 줘.
사용자에게 영향을 주는 결함과 회귀를 근거와 함께 설명해 줘.
```

```text
$acceptance-review
확정 요구와 현재 구현을 대조해 누락과 회귀를 확인해 줘.
실제 검증한 항목과 미검증 항목을 구분해 줘.
```

```text
$project-handoff
내 요청과 선택이 현재 코드에 어떻게 반영됐는지 실제 코드로 설명해 줘.
구조와 데이터 흐름, 선택의 장단점, 검증 근거와 개선 조건을 연결해 줘.
실행 방법과 남은 한계도 정리해 줘.
```

이미 만든 프로그램을 제대로 설명하기 어렵다면, 새로 구현하지 않고 다음처럼 호출할 수 있습니다.

```text
$project-handoff
현재 코드와 남아 있는 대화·결정 기록을 읽고 핵심 흐름부터 설명해 줘.
과거 지시를 확인할 수 없는 부분은 추정과 사실을 구별해 줘.
그다음 내 코드에 관한 서술 질문을 한 번에 하나씩 내고,
내가 답하면 코드 근거로 피드백해 줘. 답변 전에는 모범답안을 주지 마.
```

다음 작업을 판단하기 어려우면 `$delivery-workflow 현재 진행 상태를 확인하고 다음 작업을 추천해 줘.`라고 요청합니다. 이 스킬은 선택하지 않은 단계를 자동 실행하지 않습니다.

### 기존 기능을 바꾸거나 오류를 조사할 때

```text
$change-impact
주문 상태값 변경이 API 소비자와 기존 저장 데이터에 미칠 영향을 조사해 줘.
아직 코드는 수정하지 말고 필요한 전환과 회귀 검사를 정리해 줘.
```

```text
$root-cause-debugging
첨부한 실패 로그와 재현 입력으로 원인을 좁혀 줘.
관찰한 증거와 가설을 구분하고, 최소 수정 방향을 설명해 줘.
```

변경 영향 분석은 수정 전에, 디버깅은 실패 원인이 불명확할 때, 코드 리뷰는 변경분을 검토할 때 사용합니다. 세 스킬을 매번 추가로 실행할 필요는 없습니다.

## 작업 기록

프로젝트의 기존 문서 구조를 우선 사용합니다. 정해진 위치가 없으면 `docs/workflow/`에 단계별 기록과 `STATUS.md`를 남깁니다.

- **요구와 결정:** 실제 요청, 확정된 기준, 비교한 방식, 선택 주체와 근거
- **구현:** 결정 ID와 연결한 파일·함수·줄 위치, 입력 흐름과 선택의 효과
- **검증:** 실행 명령, 입력과 기대 결과, 실제 결과, 실패·미실행
- **인계와 이해:** 실행 방법, 완료 범위, 장단점과 개선 조건, 답변으로 확인한 주제와 남은 오해

기존 문서와 원자료를 보존하며, 기록에는 실제 결정과 실행 결과만 반영합니다. 결정 ID는 기존 것을 재사용하며 각 단계 문서에서 같은 근거를 중복 복제하지 않습니다. 파일 위치와 설명은 현재 코드 기준으로 확인하고 변경 후 갱신합니다.

질문은 지금 결정에 필요한 것부터 관련 기준을 묶어 제시합니다. 답변을 받으면 질문 번호가 없어도 의미별로 요구사항에 연결하고, 이미 확인된 내용을 반복해서 묻지 않습니다. 요구 ID와 근거는 재사용하며 긴 설명을 넓은 표 한 행에 몰아넣지 않습니다.

선택 전에는 **방식 선택 대기**, 처리와 설명 후에는 **설명 확인 대기**로 마칩니다. 현재 확인할 질문 하나에 집중하고, 핵심 설명을 문서 링크만으로 대신하지 않습니다. 기술 검사 상태와 이해 확인 상태(미확인/부분 확인/답변으로 확인/사용자 요청으로 생략)를 따로 남깁니다. 다음 단계는 사용자가 선택합니다.

테스트·리뷰 기록에서는 실패, 실행 불가, 미검증과 기준 미정을 구분합니다. 필수 항목에 실패나 미검증이 남으면 전체 완료로 판정하지 않습니다. 작은 작업에 모든 스킬을 의무적으로 호출하거나 문서를 중복 생성할 필요는 없습니다.

## 설치와 조회

이 묶음에는 **독립된 스킬 12개**가 들어 있습니다. 전체를 사용하려면 각 스킬 폴더와 그 안의 참고 파일을 함께 설치해야 합니다. 한 번의 설치 요청으로 전체 폴더를 함께 설치할 수 있지만, `delivery-workflow` 하나만 설치하면 나머지가 자동 설치되지는 않습니다.

로컬 설치는 사용할 범위에 따라 다음 위치를 선택합니다.

| 범위                                 | 위치                         |
| ------------------------------------ | ---------------------------- |
| 특정 프로젝트에서 사용               | 프로젝트의 `.agents/skills/` |
| 사용자 계정의 여러 프로젝트에서 사용 | `~/.agents/skills/`          |

예를 들어 프로젝트에 설치한 폴더 구조는 다음과 같습니다.


### 기존 설치본 업데이트

원본 저장소에서 `git pull --ff-only`를 한 뒤, 변경된 스킬 폴더를 **현재 사용하는 설치 위치**에도 반영합니다. 별도로 복사해 설치했다면 원본의 `git pull`만으로 설치본이 바뀌지는 않습니다. 설치본에 직접 수정한 내용이 있으면 먼저 비교·보관하고 필요한 변경을 병합하세요. 원본 저장소에도 로컬 수정이 있으면 덮어쓰거나 강제 초기화하지 않습니다.

오래된 지침을 이미 읽은 대화에서는 최신 `SKILL.md`를 다시 읽도록 요청하거나 새 Codex 세션에서 호출하세요. 서로 독립된 컨테이너·노트북의 설치본은 각각 갱신합니다.

## 실행 환경과 외부 스킬

이 스킬들은 개발 절차를 안내하는 지침입니다. 실제 파일 수정, 서버 실행, 테스트와 서브에이전트 사용은 실행 중인 Codex 환경의 도구·권한에 따릅니다. 설치 자체가 개발 도구나 외부 서비스 연결을 준비해 주지는 않습니다.
