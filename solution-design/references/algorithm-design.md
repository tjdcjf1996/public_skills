# 구현 전 알고리즘 설명

이번 범위의 핵심 처리마다 적용한다. 정렬·탐색뿐 아니라 집계, 조건 필터, 후보 평가, 중복 처리와 상태 전이도 알고리즘이다. 자료에 없는 요구나 과도한 최적화를 만들지 않는다.

## 설계에서 설명할 연결

1. **목적과 계약:** 어떤 요구를 해결하는지, 입력·출력·단위·유효 범위, 성공과 실패의 의미를 명시한다. 업무 기준이 없으면 질문하며 기술 선택으로 대신 정하지 않는다.
2. **대안과 선택:** 실현 가능한 대안을 같은 조건에서 비교한다. 정확성, 구현·설명 난이도, 데이터 규모, 메모리, 변경 비용을 필요한 만큼 비교하고 추천 이유와 불리한 조건을 설명한다. 유효한 방식이 하나뿐이면 억지 대안을 만들지 않는다. 사용자 선택 전 확정하지 않는다.
3. **처리 과정:** 쉬운 말로 순서를 설명하고 구현 언어에 종속되지 않는 짧은 의사코드를 보여 준다. 사용할 자료구조, 반복·분기, 상태 갱신, 종료 조건과 결과 선택 기준을 연결한다. 의사코드는 설계이며 제품 코드를 실행·구현한 것으로 표시하지 않는다.
4. **입력 따라가기:** 작은 구체적 입력을 넣어 각 단계의 중간값·남은 후보·최종 출력을 따라간다. 동점·빈 입력·중복·잘못된 값·경계값 중 해당 알고리즘에 중요한 반례도 다룬다. 기대 결과는 업무 규칙에서 도출한다.
5. **왜 맞는가:** 처리 중 유지해야 하는 조건과 모든 필요한 후보를 확인하거나 안전하게 제외하는 이유를 설명한다. 탐욕 방식·근사 방식이면 최적해를 보장하는 조건 또는 보장하지 못하는 한계를 밝힌다. 작은 예 하나의 성공으로 일반적인 정확성을 증명했다고 하지 않는다.
6. **비용과 한계:** 입력 크기 n, 후보 수 m 등 기준을 정의하고 시간·추가 공간 복잡도를 실제 반복·자료구조에서 도출한다. “O(n)은 항목 수에 비례해 처리량이 늘어난다”처럼 뜻을 풀어 쓴다. 평균·최악, 저장 공간과 작업 공간을 필요한 경우 구분한다. 측정 없이 실행시간이나 성능 향상 비율을 단정하지 않는다.
7. **구현 예정 위치와 변경 영향:** 어떤 책임·함수에 넣고 다른 부분과 무엇을 주고받을지 설명한다. 조건이나 규모가 달라질 때 바꿀 알고리즘·계약·테스트를 짚는다. 실제 코드 위치는 구현 후 연결한다.

예를 들어 요금제 추천이라면 ‘최소 비용 선택’이라는 이름만으로 끝내지 않는다. 필요한 기능·한도를 만족하는 후보를 먼저 추리는지, 총비용에 어떤 항목이 들어가는지, 동점과 후보 없음은 어떻게 처리하는지 확인한다. 어떤 비용 공식이나 동점 정책도 원자료에 없는데 임의로 확정하지 않는다.

## 이해 확인과 구현으로 넘길 조건

- 먼저 전체 구조와 핵심 알고리즘 목록을 제시하고, 알고리즘마다 설명을 나눈다. 관련 결정·이해 상태는 기존 03-design.md와 STATUS.md에 연결한다. 상세 기록을 링크로만 주고 대화 설명을 생략하지 않는다.
- 한 번에 질문 하나로 처리 순서, 선택 이유, 반례, 비용 또는 개선 조건을 자신의 말로 설명하게 한다. 모범답안은 먼저 주지 않는다. 오해가 있으면 해당 과정으로 돌아가 설명하고 재확인한다.
- 설명한 범위, 답변으로 확인한 범위, 남은 질문을 알고리즘별로 구분한다. ‘좋아’, ‘추천안으로’는 선택일 수 있지만 정확성·복잡도까지 이해했다는 증거는 아니다. 코드 한 줄 한 줄을 외우게 하거나 모든 내부 세부를 사전에 알았다고 주장하지 않는다.
- 기본 구현 준비 기준은 이번 범위의 업무 조건·구조·공통 계약과 중요한 알고리즘 결정이 정해지고, 핵심 처리와 선택 이유에 관한 이해 공백이 해소된 상태다. 정해진 문제 개수로 자동 통과시키지 않는다. 사용자가 명시적으로 이해 확인을 생략하면 미확인 항목을 남긴다.
- 준비가 되면 사용자가 구현 범위를 요청하도록 안내한다. 기획·설계 요청만으로 코딩을 시작하지 않는다. 구현 중 새 증거로 설계가 바뀌어야 하면 영향받는 결정만 다시 설명·선택하고 기록과 이해 상태를 갱신한다.
