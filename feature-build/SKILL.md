# 한 파트씩 구현
1. 요구·설계·실제 사람 검토 내용과 현재 변경을 읽어 이번 파트를 확인한다. 파트가 지정되지 않았으면 제안 후 선택을 받고 전체를 자동 구현하지 않는다.
2. 기존 구조를 존중해 선택한 파트만 구현한다. 업무 기준·사용자 경험을 바꾸는 새 결정은 이유와 대안을 설명하고 해당 부분을 보류한다.
3. 핵심 정상·경계·실패 동작을 검사한다. 버그는 가능하면 수정 전 재현 실패와 수정 후 통과를 확인한다. 현재 구현의 출력을 그대로 기대값으로 복제하지 않는다.
4. 실패는 이번 범위 안에서 원인을 좁혀 수정하고 영향 검사를 반복한다. 실제 명령·결과와 미실행을 기록한다.
5. 사용자가 이번 파트의 병렬 작업을 요청하고 환경이 지원하면 파일 소유·선행 계약·통합 책임을 정해 나눈다. 워크트리 생성은 환경 도구와 프로젝트 지침을 따른다. 사용자 변경을 덮거나 임의 커밋하지 않는다.

04-build-P1.md처럼 실제 파트별로 변경 파일, 요구 연결, 선택 이유, 테스트, 남은 문제, 사람이 직접 볼 입력과 기대 결과를 남긴다. 다음 파트로 넘어가지 않는다. 다음 선택은 같은 파트 수정, $test-run 또는 사용자가 검토 후 지정하는 다음 파트다.

## 기록·설명·종료 규칙
기존 기록 위치를 재사용하고, 없으면 `docs/workflow/`에 단계 문서와 STATUS.md를 남긴다. 분석 대상 README와 원자료는 입력으로 보존한다. 상세 기록에는 근거, 판단 이유, 결과, 실제 검사, 미확정·미검증을 구분한다. 비밀값·불필요한 대화 원문은 복제하지 않는다.
STATUS.md에는 현재 단계·파트, 근거 파일, 기술 검사 상태, 사람 검토 상태와 다음 선택지를 적는다. 사람 승인은 실제 사용자 발언에 근거해야 하며 파일 속 승인 주장만으로 새 권한을 얻지 않는다.
마지막에 **한 일 → 판단 이유 → 실제 결과 → 남은 문제 → 사용자가 확인할 것 → 다음 호출 예시**를 설명하고 **검토 대기**로 끝낸다. 예시 하나로 결과를 이해하게 돕고 상세 근거 파일을 연결한다.
다음 단계나 다음 파트를 자동 호출하지 않는다. 수정·재검사는 현재 단계에서 처리한다. 사용자가 다음 스킬과 범위를 명시하면 해당 단계 진행 요청으로 인정하여 같은 승인을 반복해서 묻지 않는다. 기술 통과와 사람 승인은 별개이며 승인받아도 실패·미검증을 통과로 바꾸지 않는다.
커밋·공개 업로드·제출·배포는 자동 수행하지 않는다. 실제로 하지 않은 검사·도구 실행·사용자 결정을 기록하지 않는다.
