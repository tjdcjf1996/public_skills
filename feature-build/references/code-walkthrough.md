# 선택이 코드가 되는 과정 설명

구현·검사가 끝난 파트마다 사용한다. 코드를 전부 낭독하거나 파일 목록만 나열하지 않고, 사용자가 주요 구조를 자기 말로 설명할 근거를 제공한다. 기존 파트 기록에 덧붙이며 별도의 문서 묶음을 의무적으로 만들지 않는다.

## 설명 전에 확인

- 실제 변경 파일과 호출 경로를 다시 읽는다. 설계 예정 경로와 현재 구현을 구분한다.
- 설계 단계의 의사코드·정확성 조건·비용 분석이 실제 함수와 자료구조에 어떻게 대응하는지 확인한다. 병렬 결과도 메인이 통합된 흐름 하나로 설명한다. 구현이 설계와 달라졌으면 코드 설명 전에 그 차이와 재선택 필요 여부를 밝힌다.
- 기존 결정 ID와 실제 요청·선택을 연결한다. 사용자 지시로 확정된 것, AI가 제안해 사용자가 선택한 것, 위임받아 AI가 정한 것을 구분한다. 선택 이유를 사용자가 직접 말하지 않았다면 AI가 설명한 이유로 표시한다.
- 선택과 구현이 어긋났으면 먼저 밝힌다. 중요한 대안으로 바뀌었다면 사후에 동의한 것으로 꾸미지 말고 현재 차이와 수정 선택을 제시한다.
- 줄 번호는 현재 파일에서 확인하고 함수·심볼을 함께 쓴다. 기준 커밋이 있으면 기록하고 미커밋 변경도 명시한다. 코드를 수정했다면 영향받는 설명·예시·검사 근거도 갱신한다. 문서화를 위해 임의로 커밋하지 않는다.

## 대화에서 보여 줄 내용

핵심을 아래 연결로 설명하되 고정된 제목이나 넓은 표로 만들 필요는 없다. 한 번에 이해 가능한 동작 하나를 설명하고, 사용자의 추가 질문에는 해당 코드까지 더 들어간다.

기본 결과 보고가 짧더라도 핵심 분기의 실제 코드 발췌는 대화에 포함한다. 함수 링크와 “검사하고 더한다”라는 요약만으로 대체하지 않는다. 발췌 아래에서 구체적인 입력의 중간값·분기·최종 결과를 따라가며, 변경 전 구조가 있다면 무엇을 왜 바꿨는지 설명한다. 사용자가 코드 발췌 생략이나 더 짧은 답변을 명시하면 그 요청을 따른다.

1. **지시와 선택:** “요청에서 A가 필요했고, B와 C 중 B를 선택했다.” 실제 근거가 있는 경우에만 사용한다. 해당 선택이 없는 과거 코드는 의도를 알 수 없다고 밝힌다.
2. **구조와 책임:** 입력을 받는 곳, 규칙을 검사하는 곳, 핵심 처리와 저장/반환을 하는 곳의 책임을 설명한다. 역할을 분리하거나 합친 이유와 맞바꾼 비용도 설명한다. 기술 용어는 바로 옆에서 쉬운 말로 풀어 쓴다.
3. **구체적인 흐름:** 실제 대표 입력 → 진입 함수 → 조건·분기 → 데이터 변환/저장 → 결과까지 따라간다. 중요한 예외 입력도 하나 보여 준다. 작은 함수·분기 발췌와 파일 경로·심볼·줄 위치를 연결한다. 전체 파일이나 비밀값은 붙이지 않는다.
4. **이로 인해 달라진 것:** 선택 → 코드 동작 → 관찰 가능한 결과를 인과관계로 설명한다. 테스트로 확인한 동작, 코드만 읽어 추론한 동작, 측정하지 않은 성능은 구분한다. “유지보수에 좋다”로 끝내지 않고 어느 규칙을 어느 함수에서 바꾸면 되는지 예를 든다.
5. **장점·대가·개선 조건:** 이 상황의 장점, 포기한 성질, 실패 가능한 조건을 설명한다. 언제 다른 방식이 유리해지는지와 바꿀 코드·계약·다시 볼 테스트를 연결한다. 불필요한 새 기능 목록을 만들지 않는다.
6. **이해 확인:** 사용자에게 구조·선택 이유·변경 영향 중 하나를 자신의 말로 설명하도록 질문 하나를 제시하고 기다린다. 설명을 듣기만 한 상태와 답변으로 확인한 범위를 구별한다. 질문 바로 뒤에 모범답안을 붙이지 않는다.

## 설명의 모양 — 가상 예시

이 예시는 형식 설명용이다. 아래 이름이나 실행 결과를 실제 프로젝트에 복사해 사실처럼 쓰지 않는다.

사용자가 “파일에 잘못된 행이 하나라도 있으면 전체를 저장하지 않겠다”고 선택했다면, 실제 코드에서 모든 행 검사 뒤 저장하는 경로를 찾아 설명한다. 파일 전체 검사가 끝나기 전에 저장 함수가 호출될 수 있는지도 확인한다.

> 전체 실패 방식을 선택했기 때문에 `importRows`가 검사 결과를 먼저 모으고, 오류가 있으면 `saveRows` 호출 전에 반환하도록 구성했습니다. 정상 행과 오류 행이 섞인 입력에서 저장 호출이 없었는지는 해당 테스트 결과로 확인합니다. 이 방식은 잘못된 자료를 일부만 반영하는 상황을 막지만, 정상 행도 오류를 수정할 때까지 반영할 수 없습니다.

여기서 **검사 후 저장한다는 구조만으로 저장 도중 오류까지 자동 복구되는 것은 아니다.** 실제로 트랜잭션이나 원자적 교체가 있는지 별도로 확인해야 한다. 없는 보장을 “전체 실패”라는 이름만으로 덧붙이지 않는다.

설명 뒤에는 “일부 정상 행만 저장하도록 바꾸면 어느 분기와 결과 표시, 테스트가 달라질까요?”처럼 지금 설명한 코드의 변경 영향을 물을 수 있다. 답변을 받은 뒤 실제 코드와 대조한다.

## 기록과 이어가기

기존 `04-build-<파트>.md`에 주요 결정별 연결과 확인 근거를 남긴다. `STATUS.md`에는 현재 코드 기준, 방식 선택 상태, 기술 검사 상태, 이해 확인 상태와 아직 설명하지 못한 주제를 분리해 기록한다. 질문에 잘 답했어도 전체 코드를 완전히 이해했다고 단정하지 않는다. 다음 파트는 사용자가 요청할 때 진행한다.
