# 구현 시작 시 실행 능력 확인과 통합

설계와 핵심 알고리즘을 설명·선택한 뒤, 사용자가 구현을 요청한 범위에만 적용한다. 병렬 처리는 실행 수단이며 설계·이해 확인을 생략할 이유가 아니다.

## 실제 환경 확인

- 현재 제공된 도구·설정에서 서브에이전트 생성, 작업 지시, 결과 수신과 상태 확인 기능을 사용할 수 있는지 확인한다. 모델 이름, 스킬 설치, 여러 터미널 또는 워크트리가 있다는 이유만으로 지원된다고 판단하지 않는다. 별도 사용자 소유 대화 생성 기능을 작업용 서브에이전트의 대체로 임의 사용하지 않는다.
- 실제 실행 제한·가용 동시 작업 수와 파일 공유 방식을 확인한다. 확인할 수 없거나 도구가 없으면 지원 미확인/미지원으로 구분하고 순차 진행한다. 지원을 만들기 위해 패키지·플러그인·로그인·권한 설정을 임의 변경하지 않는다.
- 공통 계약이 확정되고, 파일 소유를 분리할 수 있으며, 선행 작업을 기다리지 않고 독립적으로 구현·검사할 파트가 있는지 확인한다. 지원되더라도 작업이 작거나 결합도가 높으면 순차가 적합할 수 있다. 병렬화가 항상 빠르다고 보장하지 않는다.
- 메인은 확인 근거, 이번 실행 방식, 병렬 묶음 또는 순차 순서를 짧게 알린다. ‘가능하면 병렬, 아니면 순차’를 이미 요청받았으면 이 실행 방식만으로 재승인을 요구하지 않는다. 범위·알고리즘·외부 비용 등이 달라지는 경우는 별도 판단이다.

## 병렬 작업 계약

각 담당자에게 필요한 원자료와 확정 설계만 제공하고 다음을 명시한다.

- 요구·결정 ID, 선택된 알고리즘과 정확성 조건, 맡은 결과물과 완료 기준
- 수정 가능한 파일·디렉터리, 읽기만 할 공통 파일, 다른 담당자가 소유한 영역
- API·함수 입력/출력·오류·데이터 형식과 공통 계약의 버전 또는 현재 내용
- 선행 작업과 검증 사례, 실제 실행 결과·미검증·변경 위치를 돌려줄 형식
- 중요 결정이나 계약 변경이 필요하면 해당 작업을 멈추고 메인에 보고할 것

공통 타입·라우팅·의존성 파일 등 충돌 가능성이 높은 파일은 한 담당자 또는 메인이 소유한다. 공통 인터페이스가 코드로 먼저 필요하면 메인이 먼저 만들고 확인한 뒤 병렬 작업을 시작한다. 모든 파트를 한꺼번에 시작할 필요는 없다.

워크트리는 도구·프로젝트 지침과 현재 변경을 확인한 후 필요한 경우에만 쓴다. 워크트리는 프로세스·포트·데이터의 보안 격리를 보장하지 않는다. 공유 작업 폴더에서는 파일 소유를 지키며 다른 담당자의 변경을 되돌리지 않는다.

## 메인의 통합 책임

1. 실제 담당 작업의 완료·실패·진행 상태를 확인한다. 하위 작업의 보고는 근거 자료이며 자동 통과 판정이 아니다.
2. 공유 폴더라면 실제 변경을, 워크트리라면 가져올 변경과 기준 상태를 검토한다. 충돌은 확정 설계에 따라 해결하고, 의미가 달라지는 변경은 사용자 선택으로 돌린다.
3. 통합 코드의 공통 계약, 중복 구현, 데이터·오류 흐름과 알고리즘을 직접 읽는다. 통합된 상태에서 관련 빌드·테스트·실제 사용자 흐름을 검사한다. 개별 파트 통과만으로 전체 성공을 보고하지 않는다.
4. 실패는 원인 파트로 좁혀 수정·재검사한다. 에이전트를 사용할 수 없게 되면 작업 상태와 변경을 확인하고, 중복 쓰기가 멈췄음을 확인한 범위만 메인이 순차 인계한다. 살아 있는 작업 위에 같은 파일을 동시에 덮어쓰지 않는다. 중단 상태를 확인할 수 없으면 그 영역은 보류한다.
5. 메인이 확정 설계의 의사코드와 실제 함수·분기를 연결해 하나의 결과로 설명한다. 계획에서 달라진 부분과 이유, 실제 검사, 남은 위험을 밝힌다. 여러 담당자의 긴 보고를 그대로 사용자에게 쏟아내지 않는다.

순차 실행에도 같은 설계·검사·코드 설명 기준을 적용한다. 도구가 없는데 서브에이전트를 사용했다고 쓰거나, 혼자 수행한 작업을 독립 검토로 표시하지 않는다. 다음 구현 묶음이나 별도 스킬 단계는 사용자 요청 범위를 따른다.
